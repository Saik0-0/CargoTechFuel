# Заправка в рейсе

Рабочий мобильный прототип безналичной заправки. Водитель видит доступные деньги отдельно от общего лимита, подтверждает физическую колонку и резерв, после обрыва связи продолжает прежнюю операцию. Цена и итог берутся из API. Новый заказ не создаётся, пока результат предыдущего неизвестен.

## Границы решения

Проектируем выбор АЗС, топлива, физической колонки, объёма, подтверждение резерва, ожидание и фактический итог. API определяет допустимые операции. Расшифровка объясняет проблемы пользователя, но не заменяет контракт API. Макет задаёт визуальную основу, его числа примерные.

Особый риск: сервер создал заказ, ответ потерян. Клиент должен сохранять намерение до запроса и повторять только его с прежним `clientRequestId`. Запрет отмены после начала налива и фактическое списание должны быть видны пользователю.

## Запуск

Откройте `index.html` в актуальном Chrome или Edge. Рядом должны лежать `app.js` и исходный `fake-api.js`. Интернет, сборка и установка библиотек приложению не нужны. API имитирует задержки и сетевые ошибки, поэтому иногда потребуется «Проверить ещё раз».

Для демонстрации предпочтителен локальный сервер из этой папки: `python -m http.server 8000`, затем `http://localhost:8000`. Это не деплой. При открытии файла напрямую браузер должен разрешать localStorage и Web Locks. Если не разрешает, используйте localhost. Не переключайтесь между файлом, портами и адресами посреди заказа: это разные хранилища.

Разрешена одна активная вкладка. Вторая показывает объяснение и не запускает API: он держит отдельную копию состояния в памяти каждой вкладки. Чтобы перейти во вторую, закройте первую и перезагрузите вторую.

Приложение состоит из `index.html` со встроенными стилями и `app.js`. Внешних шрифтов, карт, библиотек, аналитики и сетевых ресурсов нет. `fake-api.js` скопирован без изменений. Размер двух файлов меньше 60 КБ. Проверка в PowerShell: `(Get-Item index.html, app.js | Measure-Object Length -Sum).Sum`.

## Пункт 1 Расхождения и решения

Каждая строка содержит наблюдение, решение в прототипе и основание. Прямые противоречия отделены от пробелов контракта: отсутствие поля в учебном API само по себе не доказывает его отсутствия в настоящем продукте.

### Прямые расхождения

1. **Лимиты:** макет показывает 12 450 из 20 000 ₽, разговор — около 9 300 из 20 000 ₽, API — 9 340 из 15 000 ₽; показываю `limitLeft/limitTotal` текущего рейса из API, поскольку примеры не являются его бухгалтерским состоянием.
2. **Отмена:** диспетчер разрешает отменить до половины налива, API — только `accepted/waiting_nozzle`; убираю кнопку при `fueling`, предупреждаю до заказа и обрабатываю `CANNOT_CANCEL`, поскольку клиент не может обещать неподдерживаемую операцию.
3. **Возврат резерва:** диспетчер говорит о сутках, `finish()` в API освобождает остаток сразу при закрытии заказа; показываю подтверждённый возврат конкретной операции, не обещая такой же срок для старых резервов или реальной АЗС.
4. **Чек:** макет утверждает «Чек отправлен диспетчеру», разговор описывает письмо к утру, API не даёт чека и статуса отправки; пишу, что чек недоступен и его нужно запросить у диспетчера, чтобы не сообщать выдуманный факт.
5. **Колонка:** у «Колеса» в разговоре А–Г, API требует числовой `pump`; показываю «Б · № 2» и отправляю `2`, чтобы водитель узнавал физическую стойку, а API получал свой идентификатор.
6. **Ожидание пистолета:** в разговоре около 40 секунд после сигнала, в API таймаут через 60 секунд от создания заказа, отдельного дедлайна нет; прошу готовить пистолет сразу и не рисую недостоверный обратный отсчёт.
7. **150 литров на «Колесе»:** диспетчер советует 150 л при доступных примерно 9 300 ₽, но при 71,70 ₽/л это 10 755 ₽; одновременно применяю рублёвое ограничение и `litersMax`, поскольку разрешённый АЗС объём не означает доступность покупки по деньгам.
8. **Цена:** разговор допускает 71,70 на табло и 71,71 ₽/л в приложении, API сравнивает цену заказа и возвращает `PRICE_CHANGED`; показываю цену до копеек и при изменении требую новое подтверждение суммы, потому что молчаливое согласие меняет резерв.

### Пробелы и ограничения, влияющие на сценарий

9. **История расхода:** разговор объясняет лимит покупкой и старым холдом, API не даёт разбивку; объясняю механизм, но разницу `limitTotal − limitLeft` не называю списанием и не придумываю суммы покупок.
10. **Границы рейса:** разговор говорит о пути туда и обратно, API содержит только `from/to`; пишу «общий лимит рейса» без обещания, что он выделен только на путь до Казани, поскольку обратный маршрут отдельно не задан.
11. **Прицеп:** макет содержит его номер, API — только тягач; показываю полученный `truck`, номер прицепа не копирую из макета, чтобы не привязать заказ к чужому транспорту.
12. **Рефрижератор:** разговор требует второй заказ с общим лимитом, в API нет бака; добавляю локальную пометку «Тягач / Рефрижератор» и отдельный заказ после закрытия первого, явно предупреждая, что сервер пометку не получает.
13. **Топливо:** у сетей разные торговые названия, API использует коды; показываю `fuels[].name` и отправляю `code`, поскольку «ДТ», «Дизель» и «ДТ ЭКО» могут означать `diesel`, а премиальное и зимнее топливо — отдельные позиции.
14. **Доступность колонки:** API может вернуть `PUMP_BUSY` даже после выбора свободной; обновляю данные перед подтверждением и при отказе снимаю выбор, не переключая водителя на соседнюю колонку автоматически.
15. **Топливо на колонке:** в разговоре есть предупреждение о дизеле, API задаёт `pumps[].fuels`; блокирую несовместимые комбинации и сбрасываю колонку при смене топлива, чтобы не запустить другой пистолет.
16. **Объём:** пример 150 л не подходит всем сетям, API даёт 150/300/400 л и минимум 10 л; показываю и проверяю `litersMin/litersMax` конкретной станции отдельно от доступного объёма по деньгам.
17. **Поиск АЗС:** API возвращает 300 перемешанных станций, включая дешёвую под Казанью; сначала ограничиваю список радиусом 40 км, затем сортирую по цене обычного ДТ, чтобы глобальный минимум не выдать за местную рекомендацию.
18. **Достижимость:** есть координаты, но нет дорожного маршрута, подъезда и запаса топлива; подписываю «по прямой», прошу проверить подъезд, при отказе геопозиции оставляю поиск без выдуманных расстояний.
19. **Обрыв после старта:** диспетчер запрещает повторное нажатие, API допускает безопасный повтор с `clientRequestId`; сохраняю точный запрос до отправки и повторяю только его с тем же ключом, чтобы восстановление не зависело от памяти водителя.
20. **Двойной заказ:** API не запрещает несколько активных операций и не требует ключ; блокирую повторный старт, сначала проверяю журнал и `getActiveFueling()`, поскольку недоступная кнопка сама по себе не переживает перезагрузку.
21. **Итог:** макет показывает только успех, API допускает недолив, таймаут и отказ АЗС; показываю фактические `factLiters/factAmount`, резерв и освобождённую сумму либо отмену, поскольку заказанный объём не равен факту.
22. **Восстановление:** после завершения `getActiveFueling()` возвращает `null`; сохраняю ID и проверяю `getFueling(id)` либо повторяю прежний POST, чтобы отсутствие активного заказа не приняли за доказательство отсутствия покупки.
23. **Перчатки:** разговор отмечает мелкие кнопки, промежуточных экранов в макете нет; основные действия имеют высоту от 56 px, колонки 72 px, есть крупные кнопки объёма, поскольку точный набор на клавиатуре неудобен.
24. **Вкладки:** API читает localStorage в память лишь при загрузке и не синхронизирует вкладки; удерживаю Web Lock на сессию и блокирую вторую вкладку, поскольку одинаковый ключ не исправляет две независимые копии учебного «сервера».

Разные даты разговора и API сами по себе не являются багом: материалы описывают разные срезы. Дату рейса берём из API. Соответствие букв после Г у «Колеса» предположено и явно подписано; в настоящем API нужна `displayLabel` колонки, правило А–Г также нужно подтвердить у сети.

## Пункт 3 Одно решение для владельца парка

Ровно десять строк, включая две отвергнутые альтернативы и критерий ошибки:

1. Ввожу одну меру: по умолчанию показываю дешёвые АЗС поблизости первыми, с ценой обычного ДТ и расстоянием рядом.
2. В прототипе «поблизости» означает радиус 40 км по прямой; это фильтр сравнения, а не гарантия доступного подъезда.
3. В пилот включаю только участки, где диспетчер заранее подтвердил сопоставимые по подъезду и условиям АЗС; Казань с Владимиром не сравниваю.
4. Оставляю выбор другой станции: цена литра не учитывает объезд, очередь, остаток в баке и необходимость срочно заправиться.
5. Полную трату лимита не запрещаю: покупка нужного объёма на дешёвой АЗС может быть выгодна, дробление само по себе экономии не даёт.
6. Один разработчик за две недели делает сортировку, объяснение выбора, запись ценового снимка и разделение пилота и контроля по водителям.
7. Отвергаю жёсткий потолок литров: его можно обойти повторными заказами, а дополнительные остановки и резервы ухудшат работу.
8. Отвергаю оптимальный план заправок на рейс: нужны запас топлива, расход, подъезды и будущие цены, которых нет в API и которые нельзя надёжно добавить за две недели.
9. Одна метрика — переплата на литр: сумма фактических литров × max(0, цена покупки − минимальная сопоставимая доступная цена при выборе), делённая на купленные литры.
10. Через месяц признаю гипотезу неудачной, если переплата в пилоте не ниже контроля хотя бы на 0,50 ₽/л; это заранее выбранный порог, при недостатке данных вывод неопределённый.

**Почему именно это.** Из двух жалоб напрямую обоснована переплата за топливо. «Выбрали весь лимит» требует уточнения вреда: переплата на дорогой АЗС, недостаток денег на рефрижератор позже или лишний объём? Без остатков топлива, потребности рейса и расхода автоматический запрет произволен. Сначала проверяю дешёвую обратимую гипотезу о выборе АЗС. Если проблема именно в распределении денег между баками или этапами рейса, мера её не решит: понадобятся отдельные правила владельца.

**Измерение.** На момент выбора сохранять список сопоставимых доступных станций с ценами, время и группу водителя; после закрытия связывать снимок с ID, `factLiters/factAmount`. Отмены не считать покупками, повторы ID не дублировать. Сравнивать обычное ДТ в одинаковых ценовых зонах и периодах. Группу закреплять за водителем до конца пилота. Порог 0,50 ₽/л — гипотеза минимально полезного эффекта, не статистика из материалов. Размер выборки нужно оценить по историческому разбросу до пилота, данных для обещания значимости сейчас нет.

**Граница реализации.** Прототип реализует сортировку и явный выбор. Проверка подъезда, серверная запись событий, распределение групп и расчёт бизнес-метрики — план пилота, а не выданные за работающие функции API. Сортировка не доказывает снижение расходов: проверяются фактические покупки. Выгода станции с объездом должна учитывать его стоимость до включения в сопоставимый список.

**Проверка здравого смысла на данных задания.** Среди местных станций есть ДТ по 71,46 ₽/л примерно в 26,5 км по прямой и по 71,71 ₽/л примерно в 8,18 км. На 50 л разница всего 12,50 ₽. Это не основание отправлять грузовик к первой станции: неизвестны реальный подъезд и дополнительный пробег. Поэтому интерфейс сообщает сравнение цен, но не обещает экономию от поездки к первой строке.

**План десяти рабочих дней.** Дни 1–2: согласовать ущерб и допустимые для сравнения станции, определить события и оценить выборку по истории. Дни 3–5: сортировка, пояснения, запись снимка и связи с операцией. Дни 6–7: проверка ошибок, бюджетов и качества событий. Дни 8–10: небольшой пилот, контроль фактических покупок и готовность отключить изменение. План предполагает существующий сервер операций и помощь диспетчера с доступностью станций; без них объём пилота придётся уменьшить, обещать полноценный запуск за две недели нельзя.

## Сценарий и код

Главный экран → АЗС → бак, топливо, колонка и литры → подтверждение → принятие и ожидание пистолета → налив → фактический итог. До налива можно запросить отмену. Второй бак — отдельный заказ после завершения первого с тем же бюджетом. По умолчанию объём пуст: весь лимит автоматически не подставляется.

`state` содержит экран и ввод, `render()` строит интерфейс, `validation()` проверяет формат, колонку, топливо, объём и деньги. `work()` блокирует параллельные действия. `start()` проверяет предыдущие операции, сохраняет неизменяемый запрос и вызывает `resolvePending()`. `acceptFueling()` сохраняет ID и отображает ответ. `poll()` обновляет статус с увеличением паузы при сбоях. Текст из API экранируется перед вставкой в HTML.

Деньги сравниваются в копейках, максимум литров по бюджету округляется вниз до 0,01 л. Итоговая сумма округляется до копеек как в API. Проверка клиента помогает пользователю, окончательное решение принимает API.

### Надёжность

До POST сохраняется точный запрос с ценой и ключом. Если ответ потерян, новый ключ не создаётся даже после перезагрузки. API проверяет прежний ключ до остальных условий и возвращает ту же операцию. Известные ошибки валидации возникают в данном API до создания заказа: только после такого отказа снимаем намерение и просим новое подтверждение. Неизвестная ошибка сохраняет неоднозначное состояние.

Опрос примерно раз в 1,8 секунды после ответа, при ошибках пауза растёт до 12 секунд. Одновременные опросы блокируются. При восстановлении сети и возврате в приложение статус проверяется снова. Потеря связи не означает отмену, локальный таймер не объявляет успех или возврат денег. После завершения опрос прекращается.

`localStorage` — журнал восстановления, не бухгалтерская система. При повреждении или недоступности новые заказы блокируются. Не очищайте данные браузера ради «исправления» текущего заказа: можно потерять ключ незавершённой операции. Web Locks защищает сессию одного происхождения; без него новый заказ блокируется с объяснением.

## Проверка и существенные ограничения

Проверки находятся в `tests/browser.cjs`. Это отдельный инструмент, он не подключается к странице. Нужны Node.js и установленный Playwright: `node tests/browser.cjs`; для нестандартного пути задайте `PLAYWRIGHT_PATH`, при необходимости `BROWSER_EXE`. Проверки запускают локальный сервер и браузер с изолированными хранилищами, управляют временем и ошибками, не меняя исходный API.

Проверяются успех, ограничения объёма, запятая, потерянный ответ, двойное нажатие, перезагрузка, недолив, отмена и гонка с наливом, новая цена, недостаток денег, занятая колонка, таймаут, отказ АЗС, отказ геопозиции, вторая вкладка, повреждённый журнал и два бака с общим лимитом.

Итоговый прогон: 18 браузерных проверок прошли в Microsoft Edge, включая отсутствие горизонтальной прокрутки на ширине 320 px. Файлы приложения суммарно занимают 36 616 байт. Это не проверка на физическом Android или в настоящих перчатках. Изображения главного экрана, списка АЗС, заказа, подтверждения, процесса и итога просмотрены отдельно.

- Это симулятор: отключение Wi-Fi не останавливает внутренние вызовы FakeApi. Воспроизводимые сбои проверяются ошибками API и тестовыми подменами ответов.
- Налив начинается через 10 секунд от создания, скорость 5 л/с — учебное ускорение, не норматив работы АЗС.
- Нет дорожного графа, остатка топлива, истории резервов, чека, контактов диспетчера и серверного поля бака. Их не имитируем как реальные возможности.
- После удаления localStorage, смены устройства, браузера или происхождения страницы восстановление не гарантируется. В настоящем сервисе нужны серверный журнал, поиск по ключу и запрет нескольких активных заказов в одной области лимита.
- Предположение о буквенных обозначениях после Г явно показано. Для промышленного запуска нужен справочник сети.
- Макет сохранён по смыслу и оранжевому акценту, примерные числа и неподтверждённая отправка чека заменены реальными данными API.

Репозиторий пока локальный. Перед отправкой останется вместе с участницей заполнить вопросы о первом кейсе, проверить её понимание кода и опубликовать именно эту папку в выбранном удалённом репозитории. Нейросети разрешены заданием, но защита требует собственного понимания решений.
